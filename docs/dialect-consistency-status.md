# Dialect consistency status

Reassessment of D01–D12 from the October 20, 2026 audit, against the current tree.
The audit was structural; it did not measure per-member runtime coverage. This status
records ownership and participation, not coverage parity.

| Finding                                                         | Current status                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D01: query and migration compilation ownership                  | The PostgreSQL query compiler is in [`compile.ts`](../src/dialects/postgres/compile.ts); both members own migration SQL separately in [PostgreSQL](../src/dialects/postgres/migration/sql.ts) and [SQLite](../src/dialects/sqlite/migration/sql.ts). Query and Migration remain separate Dialect facets; physical SQL and action order stay engine-specific.                                                                                                                                         |
| D02: default comparison, validation, rendering, and composition | Member [`normalize.ts`](../src/dialects/postgres/normalize.ts), [`validate.ts`](../src/dialects/postgres/validate.ts), and [`schema.ts`](../src/dialects/postgres/schema.ts) define shared ownership conventions described in [dialects](dialects.md). SQLite retains its parser and compatibility rules locally.                                                                                                                                                                                    |
| D03: helper names, identity policy, and internal exports        | Member-prefixed facet symbols and private helper ownership follow [dialect conventions](dialects.md); public indexes such as [PostgreSQL](../src/dialects/postgres/index.ts) expose only the complete Dialect and operation-session provider.                                                                                                                                                                                                                                                        |
| D04: catalog stages and evidence                                | Catalog assembly is in [PostgreSQL](../src/dialects/postgres/catalog.ts) and [SQLite](../src/dialects/sqlite/catalog.ts); SQLite's additional proof owner is [`tableProof.ts`](../src/dialects/sqlite/tableProof.ts). The shared stage guide is tracked in [#315](https://github.com/javangriff/stratom/issues/315) and [PR #326](https://github.com/javangriff/stratom/pull/326).                                                                                                                   |
| D05: unit-test location and concern split                       | Shared concern entry points include [PostgreSQL Schema](../tests/unit/dialects/postgresSchema.test.ts), [SQLite Schema](../tests/unit/dialects/sqliteSchema.test.ts), and Query, Catalog, DesiredSchema, and OperationSession counterparts. Physical migration runtime stays profile-specific: [PostgreSQL](../tests/unit/dialects/postgresMigrationRuntime.test.ts) is deterministic unit coverage; [SQLite](../tests/integration/sqlite/sqliteMigrationRuntime.test.ts) needs the native database. |
| D06: fixture names hide engine semantics                        | Engine-specific fixture modules use their member prefix, including [PostgreSQL](../tests/unit/dialects/postgresSharedFixtures.ts) and [SQLite](../tests/unit/dialects/sqliteSharedFixtures.ts); common controls stay in [unit helpers](../tests/unit/helpers).                                                                                                                                                                                                                                       |
| D07: native work in unit tests                                  | Member unit dialect fixtures use controlled providers and mocks. The architecture guard scans [dialect tests](../tests/unit/dialects) and [unit helpers](../tests/unit/helpers) for native connector and integration-runtime dependencies.                                                                                                                                                                                                                                                           |
| D08: missing shared scenarios                                   | The production [shared shard descriptors](../tests/unit/dialects/postgresSharedShards.ts) and [SQLite descriptors](../tests/unit/dialects/sqliteSharedShards.ts) supply query compiler scenarios, lowering and rejection cases, and common plus controlled provider migration participation. Unsupported query cases require a reason and rejection input.                                                                                                                                           |
| D09: shard keys and packaging                                   | [PostgreSQL](../tests/unit/dialects/postgresContractKit.test.ts) and [SQLite](../tests/unit/dialects/sqliteContractKit.test.ts) use the same `semantic`, `coordination`, and `operation-session` keys. Aggregate files own the member registration; shard and fixture modules own descriptors and construction.                                                                                                                                                                                      |
| D10: native adapter ownership                                   | The [PostgreSQL entry](../tests/integration/postgres/postgres.test.ts) and [SQLite entry](../tests/integration/sqlite/sqlite.test.ts) import reusable adapters and register each once.                                                                                                                                                                                                                                                                                                               |
| D11: package-built native smoke                                 | Both members have [PostgreSQL](../tests/integration/postgres/postgres.package.test.ts) and [SQLite](../tests/integration/sqlite/sqlite.package.test.ts) package-smoke coverage; the integration profile builds the package in [`buildPackage.ts`](../tests/integration/support/buildPackage.ts).                                                                                                                                                                                                     |
| D12: suite conventions and guardrails                           | [`dialectLocality.test.ts`](../tests/unit/architecture/dialectLocality.test.ts) checks broad entry points, registration ownership, unit/native boundaries, profile discovery, and native adapter registration. [`dialectCapabilityRegistration.test.ts`](../tests/unit/dialects/dialectCapabilityRegistration.test.ts) checks nested preflight; suite and fixture naming rules are in [dialects](dialects.md).                                                                                       |

The remaining differences are intentional: PostgreSQL carries schema namespaces,
advisory locks, and its physical AST/action order. SQLite uses the `main` alias, ASCII
identifier folding, output-name projection and value-mapping checks, metadata proof,
table rebuilds, and writer locking. Shared query forms that SQLite does not support,
including right joins, stay explicit unsupported declarations. These differences do not
imply equal test counts or measured coverage.
